# ADR-002: Frontend Clean Architecture Decisions

This document tracks architectural decisions for the Kotlin/Compose Multiplatform frontend Clean Architecture migration.

| ID | Date | Context / Decision | Rationale | Impact | Status |
| --- | --- | --- | --- | --- | --- |
| AD-012 | 2026-08-01 | Three-Layer Clean Architecture (Data → Domain → Presentation) | Enforces unidirectional dependency flow: Presentation depends on Domain, Domain defines interfaces (Repositories), Data implements them. | Domain layer has zero framework dependencies, enabling pure unit tests | Active |
| AD-013 | 2026-08-01 | Single-Responsibility UseCases | Each UseCase wraps exactly one business operation (e.g., `CreateDeviceUseCase`, `GetDevicesUseCase`). Complex ViewModels compose multiple UseCases. | Small, focused, independently testable units of business logic | Active |
| AD-014 | 2026-08-01 | Repository Interface in Domain, Implementation in Data | `domain/repository/` defines interfaces; `data/repository/` provides implementations with Ktor HTTP client and DTO-to-Domain mapping. | ViewModels and UseCases depend on abstractions, not HTTP details | Active |
| AD-015 | 2026-08-01 | Domain Models Distinct from DTOs | `domain/model/` contains framework-agnostic data classes. `data/dto/` contains `@Serializable` DTOs with `toDomain()` mappers. | Domain layer stays pure; serialization concerns stay in Data layer | Active |
| AD-016 | 2026-08-01 | Koin DI with Module Separation (Data, Domain, Presentation) | Three Koin modules: `dataModule` (ApiClient, Repositories), `domainModule` (UseCases), `presentationModule` (ViewModels). `appModules()` aggregates all three. | Clear dependency graph; `KoinModuleCheckTest` validates wiring at compile time | Active |
| AD-017 | 2026-08-01 | `koinInject()` for ViewModel Resolution in Compose WASM | Compose Multiplatform WASM does not support `koinViewModel()`. ViewModels are injected via `koinInject()` with explicit `DisposableEffect` for lifecycle cleanup (`vm.clear()`). | Consistent DI pattern across all screens; manual lifecycle management required | Active |
| AD-018 | 2026-08-01 | UiText Sealed Class for Presentation Strings | `UiText.Resource(resId)` for localizable strings, `UiText.DynamicString(value)` for server-provided messages. Contracts use `UiText?` instead of `String?`. | Eliminates hardcoded strings; enables future i18n without ViewModel changes | Active |
| AD-019 | 2026-08-01 | BaseViewModel with Abstract State Management | `BaseViewModel<S>` provides `updateState()`, `launchJob(key)` with auto-cancellation, `mapError()` for API error mapping. `BaseListViewModel<S : Paginated>` adds pagination. | Eliminates boilerplate across 11 ViewModels; consistent error handling and job management | Active |
| AD-020 | 2026-08-01 | Optional CoroutineScope Injection for Testability | ViewModels accept `scope: CoroutineScope? = null`. Production uses default `SupervisorJob()` scope. Tests pass `TestScope` (`scope = this` in `runTest {}`). `ownsScope` flag prevents `clear()` from cancelling injected scopes. | Test scheduler controls VM coroutines; `advanceTimeBy()` and `advanceUntilIdle()` work deterministically | Active |
| AD-021 | 2026-08-01 | `ApiResult.map()` Extension for DTO-to-Domain Transformation | Repositories use `apiResult.map { dto -> dto.toDomain() }` instead of `when` branching. Maps `Success` data while propagating `Error` and `NetworkError` unchanged. | Reduces repository mapping boilerplate by ~60% | Active |
| AD-022 | 2026-08-01 | Presentation Validation in VM, Business Validation in UseCase | ViewModels validate UI concerns (empty fields, field length). UseCases validate domain rules (CIDR format, octet range, prefix bounds). | Clear separation; VM validation is instant, UseCase validation is reusable | Active |
